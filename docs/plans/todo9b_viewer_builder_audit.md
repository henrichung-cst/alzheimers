### 1.1 `_write_decomp_ols_slices` — song.py:423

**Writes:**
- `edge_slices/decomp_ols/{kinase_id:03d}.parquet` — one per kinase with substrate-set motif rows
- `edge_slices/decomp_ols/index.json`
- `.build_cache/decomp_ols.json.gz` (the build cache entry)

**File count / size:** ~390 parquets, 311 MB total (from todo8 audit). The wipe-and-recreate pattern (line 470) blows away the whole directory before writing new shards, even on cache miss.

**Upstream inputs:**
- `outputs/reports/decomposition/{spine}/per_animal/site_level_ols.parquet` (`DECOMP_OLS_PARQUET`)
- `outputs/reports/kinase_attribution/mea_substrate_sets.csv`
- `outputs/reports/kinase_attribution/mea_substrate_sets_pY.csv`
- `song.py` itself (via `__file__` in the signature)

**Existing cache logic:** Full build cache (SHA-256 of each input file, plus mtime+size). `_load_build_cache` / `_write_build_cache` at song.py:129–181. Cache key includes `kid`, `contrast_to_id`, `source_columns`, `builder_version`, and `spine`. Cache file is `unified_viewer/.build_cache/decomp_ols.json.gz`.

**Change frequency:** Rare. `site_level_ols.parquet` changes only when MEA reruns. `mea_substrate_sets.csv` changes only when enrichment reruns. Both are upstream of the viewer by several pipeline stages. In practice this shard family is regenerated once per analysis cycle, not per Incytr run.

### 1.3 `_write_incytr_pair_pathways` — song.py:928

**Writes:**
- `edge_slices/incytr_pathways/{sender}__{receiver}.parquet` — one per (sender, receiver) pair
- `edge_slices/incytr_pathways/index.json`
- `edge_slices/incytr_pathways/{_INCYTR_INDEX_FILENAME}` (global filter-index binary, gzipped)
- `edge_slices/incytr_pathways/{_INCYTR_GENE_NODE_INDEX_FILENAME}` (gene-node index shard)
- `.build_cache/incytr_pathways.json.gz`

**File count / size:** ~655 files, 197 MB total (from todo8 audit). Up to 961 pair shards (31²) plus the index files. The streaming pass processes all 9 contrast parquets.

**Upstream inputs:**
- `outputs/reports/incytr_pair_mode/wide/*_incytr_output.parquet` — one per contrast (up to 9)
- `outputs/reports/snrna_integration/pseudobulk_cell_counts.csv` (for celltype QC)
- `song.py` itself

**Existing cache logic:** Full build cache. Cache key includes per-file path+mtime+size+SHA-256 for every input parquet plus the QC counts file, plus all schema/config params including `builder_version`. SHA-256 is computed by reading the full file content (song.py:96–101 `_sha256_file`). This is the most expensive signature computation: 9 parquets × SHA-256 read.

**Change frequency:** Changes on every Incytr run. This is the high-frequency family. When a new contrast is added or existing wide parquets are regenerated, all ~655 shards regenerate from scratch (even for contrasts whose parquets haven't changed, because the streaming pass is global across all contrasts and the cache is all-or-nothing).

**Key structural note:** The wipe-and-recreate of the full directory (line 1355) makes partial updates impossible — any Incytr rerun regenerates all 655 files even if only 1 of 9 contrast parquets changed.

### 2.3 What is already cached

|---|---|---|
| `decomp_ols/` | Content-hash build cache (SHA-256 per input) | Any input file change, or `builder_version` bump in `_input_signature` params |

| `incytr_pathways/` | Content-hash build cache (SHA-256 of all 9 parquets) | Any contrast parquet change |

## 3. Inefficiencies Beyond Caching

### 3.1 `PAYLOAD_JSON` (uncompressed) written but not served

`write_payload` (build_unified_viewer.py:1095–1104) always writes both `unified_viewer.payload.json` (raw, ~40 MB) and `unified_viewer.payload.json.gz` (5.6 MB). The browser only loads the `.gz` via `DecompressionStream`. The raw `.json` is:
- **Not inlined in the HTML** (default mode uses `inline_payload=False`)
- **Not referenced by the JS**
- **Uploaded to S3** by `aws s3 sync`, adding ~40 MB to every deploy

The only consumer of the raw `.json` is `validate()` (build_unified_viewer.py:1259, reads the payload back to check schema version) and `refresh_supporting_5xfad_payload()` (line 1110, reads it to patch the payload). These could instead read the `.gz` using `gzip.open`. Eliminating the raw write saves 40 MB of disk write + 40 MB of S3 upload per build.

### 3.2 `fivexfad_attribution/` and `fivexfad_celltype_mea/` use uncompressed JSON

`_write_fivexfad_attribution_shards` (fivexfad.py:615) and `_write_fivexfad_celltype_mea_shards` (fivexfad.py:819) write plain JSON. The filenames have no `.gz` extension. Combined these are 70 MB + 22 MB = 92 MB on disk. Gzip at compresslevel=6 would bring these to roughly 20–30 MB. Contrast with `_write_fivexfad_detail_shards` (fivexfad.py:1366) which correctly writes `.json.gz`. The JS-side shard loader would need to handle both formats — a contract change. If the JS already handles `.json.gz` for `fivexfad_detail`, it can handle it for attribution and celltype_mea too, but this needs a JS change.

### 3.3 `_write_fivexfad_detail_shards` reads all CSV files upfront into DataFrames

At fivexfad.py:1163–1169, for each of 4 (tissue, track) specs, the function reads 6–7 CSV files entirely into memory before processing any kinase. These are not large files (per-5xFAD-sample CSVs), but the read is unconditional even if the shallow cache check would skip the rebuild. The shallow cache check (fivexfad.py:1107–1119) is done before these reads, so this is only a problem when the cache is cold. Not a major issue in practice.

### 3.4 `_sanitize(payload)` runs on the full assembled payload

`_sanitize` is called at build_unified_viewer.py:1092 on the complete assembled payload dict (~40 MB in-memory). This is a recursive NaN-to-None and numpy-scalar-to-Python conversion. It runs on every build, cannot be cached, and has to traverse the full object graph. Its cost is bounded by payload size and is unlikely to be a bottleneck, but it runs even when only a small slice changed.

### 3.5 `_write_incytr_pair_pathways` SHA-256 computation on cache miss is expensive

The cache signature for `incytr_pathways` computes SHA-256 of every input parquet (song.py:96–101, `_sha256_file`). For 9 parquets totaling ~1 GB, this reads ~1 GB of data just to compute the cache key — before any shard regeneration begins. On a cache hit this is paid once per build. There is no fast path using only mtime+size; the current `_file_fingerprint` always computes SHA-256 (song.py:103–115). This is correct but expensive for the high-frequency family. For parquets whose mtime+size is unchanged, mtime+size alone is sufficient — SHA-256 adds protection against in-place modification, which does not occur in this pipeline (parquets are atomically replaced by the Incytr runner).

### 3.6 `_annotate_trajectory_columns` in `song.py` and `_5xfad_annotate_trajectory_columns` in `fivexfad.py` are near-identical

The two functions (song.py:673 and fivexfad.py:1610) implement the same pivot-and-label logic with different timepoint sets. This is not an inefficiency per se (different number of timepoints) but represents duplicated logic that could share a common implementation with timepoint_set as a parameter. Not a performance issue, but a maintenance risk.

### 3.7 Build cache files themselves are SHA-256-gzipped JSON — cold start reads them twice

`_load_build_cache` (song.py:129) reads the cache JSON, then verifies that each listed output file exists on disk. If any output file is missing (e.g., after a manual `rm -rf edge_slices/decomp_ols/`), the build cache is considered stale and the full regeneration runs. This is correct behavior. However, the cache file is read even on a cache miss (to compare signatures), and then re-read by `_write_build_cache` on completion (not re-read — it overwrites). No double-read issue here.

### 3.8 `_write_fivexfad_detail_shards` writes JSON through a parts_dir intermediary then re-reads parts

fivexfad.py:1347–1357: individual (kinase, key) payloads are written to `parts_dir` as JSON files, then read back (line 1357: `json.load(f)`) and merged into a per-kinase bundle. This double write-read per part is unnecessary — the payload dict is already in memory before the `json.dump` call at line 1348. The parts_dir pattern was used to allow multiple analysis_tracks to be processed sequentially and then merged per-kinase, but the payload dict could be accumulated in a `dict[str, dict]` in memory instead of using the filesystem as a staging area. This would eliminate ~2× the file I/O for this shard family.

### 3.9 `ensure_measurement_trace_sources` reads the full Excel workbook every cold build

build_unified_viewer.py:399: `pd.read_excel(kattr.TOTAL_PROTEOME_FILE, header=1)` loads the full total-proteome workbook. Excel workbooks are not streamable; the full file is loaded into memory. On a cold build (schema version mismatch or first build), this is unavoidable. On a warm build (correct schema version), the function returns early at line 389. The risk is that the schema version is a monotonic constant, not a content hash — if the workbook changes (new samples added), the existing trace CSVs are never updated until someone manually bumps `MEASUREMENT_TRACE_SCHEMA_VERSION`.

## 4. Caching Implementation Plan (Option B)

The build cache system for Song shard families already exists in `song.py` (`_input_signature`, `_load_build_cache`, `_write_build_cache`, the `.build_cache/` directory). The gap is:

1. Three shard families that have no cache at all (human_perdonor, 5xFAD attribution, 5xFAD celltype_mea)
2. Two 5xFAD families with a shallow cache that doesn't check input content (fivexfad_detail, fivexfad_celltype_ols)
3. The high-frequency `incytr_pathways` family has a correct cache but SHA-256 is computed on every build even on cache hit — mtime+size would be sufficient for the quick-check path

### 4.1 Manifest location and schema

The existing cache directory is `outputs/reports/unified_viewer/.build_cache/`. Each family has one file: `.build_cache/{family}.json.gz`. This is already implemented for `decomp_ols`, `song_concordance`, and `incytr_pathways`. The same directory and format should be used for new families.

**Cache entry schema** (current):
```json
{
  "cache_schema_version": 1,
  "family": "decomp_ols",
  "input_signature": {
    "cache_schema_version": 1,
    "family": "decomp_ols",
    "params": { ... },
    "files": [
      { "path": "relative/path", "size": 12345, "mtime_ns": 1234567890, "sha256": "abcdef..." }
    ]
  },
  "output_files": ["000.parquet", "001.parquet", "index.json"],
  "payload": { ... }
}
```

The `payload` field stores the return value of the shard writer (the index dict). This is what's returned on a cache hit instead of re-reading the index.json from disk.

**Schema invalidation:** The `cache_schema_version` field in the signature is currently hardcoded to `_BUILD_CACHE_SCHEMA_VERSION = 1` (song.py:77). A schema version bump in `song.py` (or the equivalent in fivexfad.py once the cache is ported there) invalidates all entries for that family.

### 4.2 Fast vs. strict hash mode

The current implementation always SHA-256s every input file, even on a potential cache hit. A two-phase approach would be faster:

**Phase 1 (cheap):** Compare mtime_ns + size for all input files. If all match the cached values, treat as a hit without reading file content.

**Phase 2 (strict):** Only run SHA-256 when mtime or size differs (catching in-place modifications). For this pipeline in-place modification of upstream parquets does not occur (Incytr atomically replaces files), so Phase 1 alone is sufficient. However, keeping Phase 2 as the fallback preserves correctness guarantees.

Implementation: change `_load_build_cache` to first try the cheap path (mtime+size match only), and return early without SHA-256 if all files pass. This would eliminate the ~1 GB read on `incytr_pathways` cache hits.

```python
def _load_build_cache(family, signature, output_dir, *, strict=False):
    ...
    cached_files = cached["input_signature"]["files"]
    current_files = signature["files"]
    # Fast path: mtime+size only
    if not strict:
        for cf, sf in zip(cached_files, current_files):
            if cf.get("missing") or sf.get("missing"):
                if cf.get("missing") != sf.get("missing"):
                    return None
                continue
            if cf["size"] != sf["size"] or cf["mtime_ns"] != sf["mtime_ns"]:
                return None
        # All mtime+size match; skip SHA-256 comparison
        ... check output files exist ...
        return cached.get("payload")
    # Strict path: full signature comparison (includes SHA-256)
    if cached["input_signature"] != signature:
        return None
    ...
```

The `_input_signature` function would still compute SHA-256 for the cache-write path (to record the true fingerprint), but not for the cache-read path.
