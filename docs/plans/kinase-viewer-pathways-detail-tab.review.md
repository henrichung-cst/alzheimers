## Merit
The plan is domain-sound and well-grounded in the actual code. It is the kinase-first inverse of the existing pathway-first sidechain graph, and it consumes the exact computation that just landed (`_incytr_pathway_participation`, `_read_terminal_edges`, `_build_terminal_kinase_lookup`) rather than reinventing the terminal-edge rule. The count-0 exclusion is correctly justified: those observed changes are never drawn in any sidechain, so restricting the tab to per-edge count ≥ 1 keeps it consistent with the "sidechain-drawable set." The distinct-row union semantics (`#pathways` = union of role masks, `#backbones` = Receptor∪EM, breakdowns as role-membership vs. partition) are stated precisely and match the composite-key scan already in `slices_kinase.py:609`. Verification is concrete and falsifiable (headline == Explorer columns, `by_contrast`/`by_receiver` sum to `#pathways`, `#backbones` ≤ `#pathways`, every listed edge ≥ 1, spot-check one cross-link, report payload/sidecar sizes, `file://` degradation, `node --check`). The memory-capped build is prudent given the 78 MB source and ~1.87M-row index. File and function citations are accurate once basenames are resolved: `renderKinaseDetail`/`KINASE_AUDIT_TABS` map (`viewer_shared/.../kinase_detail.js`), `AuditDataStore` (`01_state.js:400`, `fileMode`/`relative_path`/`preview` all real), `_audit_csv_meta` manifest shape (`slices_audit.py:143`), the any-role exact gene match (`incytr_pathways.js` `_ipRowHasExactGeneSearchValue`), and the `IncytrFilter.set(...)` + `SET_VIEW activeTab:"incytr"` handoff (precedent in `temporal_v2.js:526`).

## Parsimony
One minor smell.

- Shotgun Surgery / Divergent Change — `build_tcell_viewer.py` step, "wire the Explorer column counts from the same block." The Explorer columns today read the columnar arrays `K.incytr_pathway_count` / `incytr_backbone_count` (set on the kinases slice at `build_tcell_viewer.py:250`, consumed at `kinase_explorer.js:205`). Re-sourcing those columns to a new name-keyed `kinase_incytr_participation` block re-touches working display code that landed only a few commits ago, for zero change in displayed value, and leaves two representations of the same counts in flight. Plainer alternative: compute counts once in the extended scan and populate BOTH the existing columnar arrays (Explorer JS unchanged) and the new name-keyed block (detail tab). The block then carries only what is genuinely new — the three breakdowns — and no Explorer JS is edited. This preserves the "one scan" claim without the JS rewire.

Everything else is appropriately lean: the deferred contrast-narrowing ("only if the MEA contrast maps cleanly — verify at implementation") is a genuine open question, not speculative generality; the raw-string `contrast` threaded through `_terminal_contrast_to_row` is the documented row-vocabulary convention, so no Primitive-Obsession flag; inlining the small summary while lazy-loading the edge sidecar mirrors the existing audit degradation pattern rather than duplicating it.

## Cohesiveness
Strong fit. The tab slots into the established `KINASE_AUDIT_TABS` + `renderActiveKinaseAuditTab` else-if pattern; because the shared `kinase_detail.js` simply maps over `KINASE_AUDIT_TABS`, conditionally appending the tab in the tcell-side array needs no shared-file edit. Lazy-load reuses `AuditDataStore.load` + `AuditTable` verbatim, the sidecar registration reuses the `_audit_csv_meta` manifest shape, and the summary compute extends the existing composite-key scan rather than adding a pass. Cross-nav reuses the `IncytrFilter` field set already exercised by `temporal_v2._temporalOpenPathways` and the heatmap handler. The repo already performs the adjacent operation — the pathway-first sidechain (`_write_tcell_sidechain_slices`, `_build_terminal_kinase_lookup`) — and this plan correctly links to it rather than duplicating a graph. The only friction is the Explorer re-sourcing noted above.

## Decomposability
Exceeds half a day (composite-key mask correctness + per-edge count map + count-0 drop on the Python side, plus a full JS tab with lazy-load, cross-nav, and `file://` degradation, plus a memory-capped rebuild of a large viewer and its verification). Separable along one clean interface — the payload block + sidecar manifest schema:

- Workstream A — Backend compute & delivery (Python): extend the scan in `slices_kinase.py` for `by_role`/`by_contrast`/`by_receiver` and per-edge pathway counts; build the compact participating-edge rows in `slices_incytr.py`; assemble the inlined block, write the sidecar, and register it in `build_tcell_viewer.py`. Clean boundary because its entire output is a documented data contract (block shape + manifest entry) verifiable independently against the existing Explorer column values.
- Workstream B — Frontend tab (JS): the `else if (tab === "pathways")` branch in `kinase_audit.js` — summary render, expander lazy-load via `AuditDataStore`, slice by `ctx.name`, cross-nav handoff, `file://` note, empty state. Clean boundary because it depends only on the agreed block/sidecar shape and can be built against a fixture.

The two meet only at the payload/manifest schema, so agreeing that shape first lets them proceed in parallel. Decomposability is satisfied and does not force the verdict.

## Suggested changes
1. Do not rewire the Explorer columns to the new block. Keep `kinase_explorer.js` reading the existing `incytr_pathway_count` / `incytr_backbone_count` arrays; have the extended scan populate both those arrays and the new name-keyed `kinase_incytr_participation` block from the same computation. Rationale: avoids churning display code that landed only a few commits ago, eliminates the two-representations-in-flight risk, and still honors the "one scan, no duplication" intent — the block then adds only the genuinely new breakdowns.
2. Before building, pin the sidecar/manifest schema as the explicit interface between the two workstreams (column set, `type`, empty-`preview` convention, `relative_path`), matching an existing `_audit_csv_meta` entry exactly. Rationale: it is the single coupling point between workstreams A and B and the thing most likely to drift; fixing it up front is what makes the parallel split clean.
3. In verification, add an explicit sidecar row-count/size check for the largest-participation kinases (max 1554 edges) and confirm the whole-table-fetch-then-client-slice pattern stays acceptable at the total participating-edge volume. Rationale: `AuditDataStore` fetches and caches the entire table; the plan should confirm the surviving-edge total keeps that single fetch reasonable, since the summary already covers the common case and the edge table is opt-in behind the expander.
